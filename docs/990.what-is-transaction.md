# What is a Transaction in MySQL?

## Definition

A transaction is an **indivisible unit of work** in a database.  
Every step inside either **succeeds completely (COMMIT)** or **fails completely (ROLLBACK)** — there is no in-between state.

Real-world example: a bank transfer.

```
Alice sends $100 to Bob:

  Step 1 — Debit $100 from Alice
  Step 2 — Credit $100 to Bob

If Step 1 succeeds but Step 2 crashes:
  → Without transaction: Alice loses $100, Bob receives nothing
  → With transaction:    ROLLBACK — Alice still has her $100
```

---

## ACID — The 4 Properties of a Transaction

| Property | Meaning |
|---|---|
| **A**tomicity | All or nothing — no partial results |
| **C**onsistency | Data is always valid before and after the transaction |
| **I**solation | Concurrent transactions cannot see each other's intermediate state |
| **D**urability | After COMMIT, data is permanent even if the server crashes |

## Demo 1 — COMMIT (Happy Path)

### Concept

```sql
START TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- debit Alice
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- credit Bob
COMMIT;
```

Both UPDATE statements are only **permanently written to the DB after COMMIT**.  
While the transaction is running, other connections still see the old balances.

### Call the API

```bash
POST /api/v1/demo/transactions/commit
Content-Type: application/json

{
  "from_account_id": 1,
  "to_account_id":   2,
  "amount":          "100"
}
```

### Expected response

```json
{
  "demo": "COMMIT",
  "explanation": "Both debit and credit committed atomically. Other connections only see the new balances after COMMIT.",
  "before": [
    { "id": 1, "owner": "Alice", "balance": "1000.00" },
    { "id": 2, "owner": "Bob",   "balance": "500.00"  },
    { "id": 3, "owner": "Carol", "balance": "250.00"  }
  ],
  "after": [
    { "id": 1, "owner": "Alice", "balance": "900.00" },
    { "id": 2, "owner": "Bob",   "balance": "600.00" },
    { "id": 3, "owner": "Carol", "balance": "250.00" }
  ]
}
```

**What to observe:** `before` → `after` changes correctly on both sides.  
Alice decreases by $100, Bob increases by $100. The total money in the system is unchanged.

## Demo 2 — ROLLBACK (Mid-transaction crash)

### Concept

```sql
START TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- debit Alice ✓
  -- !!! error occurs here (API timeout, exception, ...) !!!
ROLLBACK;  -- MySQL undoes the debit, Alice gets her $100 back
```

This is what happens **without a transaction**:

```
Step 1 succeeds: Alice loses $100
Step 2 crashes:  Bob receives nothing
Result:          $100 disappears from the system
```

### Call the API

```bash
POST /api/v1/demo/transactions/rollback
Content-Type: application/json

{
  "from_account_id": 1,
  "to_account_id":   2,
  "amount":          "100"
}
```

### Expected response

```json
{
  "demo": "ROLLBACK",
  "explanation": "Debit ran but a failure occurred before credit. MySQL rolled back the debit — sender balance is unchanged.",
  "error": "Payment gateway timeout — simulated failure.",
  "before": [
    { "id": 1, "owner": "Alice", "balance": "900.00" },
    { "id": 2, "owner": "Bob",   "balance": "600.00" }
  ],
  "after": [
    { "id": 1, "owner": "Alice", "balance": "900.00" },
    { "id": 2, "owner": "Bob",   "balance": "600.00" }
  ]
}
```

**What to observe:** `before` and `after` are **identical**.  
Even though the debit ran, ROLLBACK undid it — Alice did not lose any money.

## Demo 3 — SAVEPOINT (Nested transactions)

### Concept

MySQL allows creating "save points" inside a transaction.  
If the later part fails, only that savepoint is rolled back — the earlier part is untouched.

```sql
START TRANSACTION;

  UPDATE accounts SET balance = balance - 50 WHERE id = 1;  -- debit Alice for B
  UPDATE accounts SET balance = balance + 50 WHERE id = 2;  -- credit Bob ✓

  SAVEPOINT sp1;

    UPDATE accounts SET balance = balance - 50 WHERE id = 1;  -- debit Alice for C
    -- !!! error occurs here !!!
  ROLLBACK TO SAVEPOINT sp1;  -- only undoes everything after sp1

COMMIT;  -- A→B is still committed normally
```

Laravel automatically uses SAVEPOINTs when `DB::transaction()` calls are nested.

### Call the API

```bash
POST /api/v1/demo/transactions/savepoint
Content-Type: application/json

{
  "from_account_id":  1,
  "to_b_account_id":  2,
  "to_c_account_id":  3,
  "amount":           "50"
}
```

### Expected response

```json
{
  "demo": "SAVEPOINT",
  "explanation": "Outer transaction (A→B) committed. Inner savepoint (A→C) rolled back independently. Outer COMMIT is unaffected by the inner failure.",
  "savepoint_error": "Inner transfer to Account C failed — simulated.",
  "before": [
    { "id": 1, "owner": "Alice", "balance": "900.00" },
    { "id": 2, "owner": "Bob",   "balance": "600.00" },
    { "id": 3, "owner": "Carol", "balance": "250.00" }
  ],
  "after": [
    { "id": 1, "owner": "Alice", "balance": "850.00" },
    { "id": 2, "owner": "Bob",   "balance": "650.00" },
    { "id": 3, "owner": "Carol", "balance": "250.00" }
  ]
}
```

**What to observe:**
- Alice decreases by $50 (only for Bob, not Carol).
- Bob increases by $50 — outer transaction committed successfully.
- Carol stays at $250 — inner savepoint was rolled back, Carol received nothing.

## Demo 4 — Insufficient Balance

## Why does debit need `lockForUpdate()` but credit does not?

### The race condition without a lock

```
Connection A reads: Alice balance = $1000  →  1000 >= 500 ✓
Connection B reads: Alice balance = $1000  →  1000 >= 500 ✓  (same moment, sees old value)
Connection A writes: balance = 500
Connection B writes: balance = 500         ←  WRONG — should be $0
Result: Alice transferred $1000 but only lost $500
```

### The 3 lock types in MySQL

| Lock | SQL | Allows | Blocks |
|---|---|---|---|
| No lock | `SELECT` | Everyone reads freely | Nothing |
| Read lock | `SELECT ... LOCK IN SHARE MODE` | Multiple readers | Writes |
| **Write lock** | **`SELECT ... FOR UPDATE`** | **Only me — read + write** | **All other locked reads and writes** |

`lockForUpdate()` in Laravel generates `SELECT ... FOR UPDATE`.  
It locks at read time — protecting the entire **"read → check → write"** chain from a race condition inserting itself in between.

```
Connection A:  SELECT ... FOR UPDATE   ← acquires exclusive lock
Connection B:  SELECT ... FOR UPDATE   ← BLOCKED, must wait
Connection A:  UPDATE balance = 500
Connection A:  COMMIT                  ← lock released
Connection B:  SELECT ... FOR UPDATE   ← can now read, sees balance = 500
Connection B:  500 < 500 → guard fails ← correct
```

### Why credit does not need a lock

| | Debit | Credit |
|---|---|---|
| Can corrupt data? | Yes — balance can go negative | No — only increases, no invariant to protect |
| SQL executed | Read → check → write (3 steps) | `UPDATE balance = balance + X` (1 atomic step) |
| Needs lock? | **Yes** | **No** |

MySQL's `INCREMENT` is atomic at the SQL level — there is no gap between read and write for a race condition to slip through.

### What Eloquent actually generates under the hood

`$account->increment('balance', $amount)` generates a **single** SQL statement:

```sql
UPDATE accounts SET balance = balance + 100 WHERE id = 2
```

The arithmetic happens **inside the MySQL engine** — PHP never touches the value.  
There is no gap between read and write, so no race condition can slip through.

---

**The naive Eloquent update — this IS dangerous:**

```php
// ❌ UNSAFE — two separate DB round-trips with a gap in between
$account->balance = $account->balance + 100;  // PHP reads here
$account->save();                              // PHP writes here
```

Eloquent's `save()` generates:

```sql
-- Trip 1: PHP reads the current value
SELECT * FROM accounts WHERE id = 2          -- PHP gets balance = 500

-- Trip 2: PHP writes back a hardcoded number
UPDATE accounts SET balance = 600 WHERE id = 2
```

Race condition with two concurrent connections:

```
Connection A reads:  balance = 500  (PHP)
Connection B reads:  balance = 500  (PHP)   ← sees stale value, gap exploited
Connection A writes: balance = 600
Connection B writes: balance = 600          ← WRONG — should be 700, $100 lost
```

---

**The rule for Eloquent credit operations:**

```php
// ✅ Safe — arithmetic inside MySQL, single atomic statement
$account->increment('balance', $amount);   // UPDATE SET balance = balance + X

// ❌ Unsafe — arithmetic in PHP, two trips, race condition possible
$account->balance = bcadd($account->balance, $amount, 2);
$account->save();                          // must add lockForUpdate() if you use this pattern
```

**Summary:**

| Eloquent method | Generated SQL | Atomic? | Lock needed? |
|---|---|---|---|
| `increment()` / `decrement()` | `SET balance = balance + X` | **Yes** — single DB operation | **No** |
| `$model->field = X; save()` | `SELECT` then `UPDATE SET balance = X` | **No** — two separate trips | **Yes** |

## Full code flow

```
POST /api/v1/demo/transactions/commit
  │
  ├── TransferRequest::rules()          — validate from_id, to_id, amount
  │
  ├── TransactionDemoController         — calls service, returns JSON
  │
  ├── TransactionDemoService            — DB::transaction(), guardBalance()
  │     └── throws InsufficientBalanceException if balance is too low
  │
  ├── EloquentAccountRepository
  │     ├── debit()  — SELECT ... FOR UPDATE → decrement
  │     └── credit() — increment (no lock needed)
  │
  └── AccountResource                   — formats the response
```
